# 小红书城市报告

只给城市时先发现当地怎么玩，再整理食宿、避坑和交通。优先查有具体店名、多店对比和分项价格的合集，一篇可贡献多个地点。指定样本数时依指定执行。

1. 日常城市优先多店合集和横评，通常核读 10–15 篇；线路、体验和生活信息都有可用证据、关键价格可溯源就停止。按笔记 ID 去重，只对缺少有效选项的维度补搜。用户要求深度版时再以 30–40 篇候选、去重后 25–35 篇为目标。查询用「城市 + 实踩雷/近期变化」「美食合集 人均 实付」「住过几家酒店 对比」「青旅 横评 床位」「机场/车站 进城 换乘」，按缺口单独补搜。每类可以返回多项。回归用 5 篇时注明小样本。
2. 低频人工打开公开原帖或使用用户分享的正文。站内有正常可用的 rednote.com 会话也可读取。仅取最近 12 个月，日期缺失先补核，只有编辑时间时勿当成首次发布时间。只有月日时记录推定年份与依据。原文、作者主页 ID、来源链接、日期口径、评论采样状态分别保存。广告和疑似商业帖留在审核记录，排除统计。
3. 评论优先取点赞前 10–20 条。可获取全部时按赞排序取前 20，少于 10 条则取全部；原站已按点赞排序时取前 20。验证不了排序或完整性就标「未核实」，跳过评论票数与更正，不将默认列表称为热评。只摘相关结论，点赞排序不代表事实准确。
4. 逐帖执行 [提取 prompt](references/extract-v1.md)。每篇保存一个 JSON。先复用已有笔记 ID 的输入和提取缓存。仅原文、评论样本或提取 prompt 更新时重提取。名称对齐按城市、分店和问题类型判定，显式别名用 aliases 文件维护；旧资料无逐字证据时仍可回看，补核后方可进入新报告。
5. 同城按维度和规范名聚合；按作者主页 ID 去重计票。每条附提及人数、推荐与避雷票、日期及原帖。只有一篇来源标「单一来源」，多篇但同作者另标。不足十项避坑时列出实际条数。正文与更新分开追溯，同店较新的可信评论优先展示，未经证实的关店传闻保留为待核。过期材料仅计入「可能过期」排除项。正文只写有依据、能帮助选择的玩法、菜品、住宿和提醒。省略抵达交通、空栏目、未找到的内容和缺价说明。价格有实付或人均依据时才写，并保留单位。文章简短，每项一两句，来源放在句末。「吃什么」用项目列表，每家店独占一行，店名在前，接推荐菜和有依据的实付或人均价格。计票与采集情况保存在逐项证据；需要导出明细时用 report --evidence。

国内城市先查高德全城美食榜与大众点评同城必吃榜，每源取前十。高德记录榜单年份及原名次；大众点评记录「全城、全部美食、综合排序」的展示位置与日期。同城同分店对齐，全名含分店的双榜重合项优先核实，两个榜的其余候选也分别查小红书。景点优先取高德同城景点榜。用 collect_city.py；首次从官方必吃榜页定位城市，用 --dianping-city-id 传入 cityid，核对页面城市后程序记住编号。输出 城市双榜.json 和 双榜对照.md。仅品牌相同不可替分店背书。若用户没有另选来源，单个平台不可读取就保留能取得的榜单并记录状态；两个平台均无覆盖的类别回到城市名盲搜。海外来源以 Waymark/DestinationSources.json 为准。用米其林必比登和地区指南（日本加 Tabelog）发现餐厅，用 Tripadvisor 和官方文旅、景区资料发现并核对景点。餐厅与景点均记录同一地点的 Google Maps 评分、评价数、核对日期和门店链接。沿用 Waymark 筛选门槛：4.6 分起；餐厅 300 条评价起，景点须有真实评价数。

餐厅先用城市名做盲搜，分别查综合清单和人气小馆的实吃记录。整理时对照独立作者与原帖，若整张清单只引用同一篇，先用不同作者的实际点单补搜；用户给出的店名另做定向核实，单独记录是否由盲搜发现。平台星级按同一分店核对，附评价数；作者个人打分与榜单收录分开记录。

## 玩法发现与验收

先查当地自由行或多日综述，优先读不同作者。从各类已读原帖一起找线索，包括作者自命名的行程小标题与特色体验清单；即使写在食宿或交通帖中也要检查。以原帖真实出现的路线名、片区、地点及活动生成下一轮检索词。用同一段里提到的地点与体验补搜，区分独立作者与重复转述。不同城市可以有完全不同的玩法结构。经典线路、地理片区、自然活动、文化生活只是审视缺口的角度，不要求每座城市凑齐每一项。
复核补搜词时，检查它是否只是“来＋目的地”或“徒步下山”等动作被错当成地点；遇到这种情况，回到原文选具体地名，再判断新增笔记是否补足了缺口。美食合集里的「收藏未去」不能计作作者亲访。
默认玩法最多追加三次查询，每次最多收录一篇新原帖。记录各次查询、命中来源、原文和仍待核实的线索；只搜酒店等单一主题或用户指定明确关键词时保持窄范围。根据“能否比较当地主要玩法、有没有区别于同一类地标的体验、每项能否溯源”验收报告。不要把有搜索结果当作已经证实，也不要在正文出现多个当地线路时只挑几个拍照点。Mac 检索记录见当次目录的 玩法检索.json。回归样本使用暹粒的不同圈线及湖上活动，另用不同目的地检查城市专名不会从上个城市泄漏。

## 本地使用

评测检索工具时，分别计时首次安装、登录检查、实际搜索与缓存重放。未登录或搜索接口报错时，把召回率记为「未测」，保留原报告，并结束该会话的批量查询。用沈阳小见野酒店帖回归检查楼中楼：只有获取到对应作者的询价回复，才把 240 多元记为作者当次订价。

扫码后确认浏览器实际登录的站点，使用对应站点模式。当页面同时显示「没找到相关内容」和拼图验证时，记录为等待本人验证，不能计为零命中。接口的 RetryError 本身不能判定登录过期。登录检查返回 false 时检查是否有连接超时；同一会话的站内网页已正常返回搜索结果时，可以用一次正常检索验证客户端。记录城市词、分类词、已知店名或作者定向补查各自的命中数，最后一类只用于找回旧帖。核对价格回复时比对笔记作者与评论作者的账号 ID。

使用 Python 3.11+。人工样本目录每篇一个 JSON，含 source 与 extraction；source 的字段和输出约定见 prompt。source.comments_mode 可为 all、top_likes 或 unverified。评论给 id、author_id、date、likes（未知可 null）、text、basis（author / firsthand / unconfirmed）。source.body 可保存经核对的相关短摘录，注明范围。

- `python3 scripts/city_report.py import 样本目录 --db 缓存.sqlite` 校验证据，更新 SQLite。内置 Claude 调用模式用 `extract 原始目录 --model 模型名 --db 缓存.sqlite`，从环境读取 ANTHROPIC_API_KEY；原始目录每篇含 source。只发送未缓存的公开笔记，日期筛选用 --as-of。
- `python3 scripts/city_report.py report 城市 --db 缓存.sqlite --as-of YYYY-MM-DD` 输出 Markdown，不调用模型。可传 --aliases 指向 JSON 对照表，键为「城市|维度|别名」，值为已核对的规范名；改排版或对齐名称不重提取。
- 旧 places/notes 数据继续由 scripts/rank_notes.py 回看。验证顺序是先跑 5 篇，再评估 20–30 篇人工集。当前流程不依赖自动抓取。将报告、逐帖 JSON、缓存和候选记录保存在项目 output/xhs-travel/城市-日期 目录，答复给出实际文件链接。同日重跑另存版本或追加，保留历史结果。

## 个人版 Mac 与 iPhone

Mac 上用户要求搜索城市时，先看该城市已保存的报告，再用本地 MediaCrawler 查缺口。用独立环境的 Python 调用本 skill 的 `scripts/collect_city.py`，例如 `"$HOME/Library/Application Support/Waymark/MediaCrawler/venv/bin/python" ~/.codex/skills/xhs-travel-notes/scripts/collect_city.py 沈阳 --output "$PWD/output/xhs-travel/沈阳"`。默认每类取两篇已读原帖，指定主题用 --topic 和 --keywords。默认浏览器为本工具自己的持久化窗口，首次登录后复用。已手动开启的专用会话可显式指定 --session-dir。不要使用日常浏览器配置。来源包 sources/ 与 city_report.py 的提取、校验及汇总兼容。每次另存新目录，失败保留已读资料。手机用 waymark-plan.json；需要直接传到配对手机时用 --iphone 及用户指定的设备标识。

iPhone 的「行程 → 城市 → 小红书旅行攻略」独立联网，按应用内 TravelTopics.json 查玩法及原有五类的首批可读结果，在本机按笔记 ID 合并，并尝试摘取每类首篇的正文。在系统端侧模型可用时从已有原文选取可逐字核对的要点。手机号登录或验证只由用户在站点界面完成。实际未取得的正文、评论和价格不作推断。设备切到后台可能暂停；保存已完成的类别，回到页面继续。此入口与要求配对核分的 Google Maps 城市榜单独立。
